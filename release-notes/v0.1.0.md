The first release. The interfaces below changed shortly before it; code written against earlier development builds needs these changes.

- **`HttpOptions::headers`** (feature `http`): extra headers sent with every request to every relay, for a relay behind a proxy that asks for a token. Their values never appear in the `Debug` output of the options or of the client, and a header HTTP does not allow is refused without echoing its value.
- **An `HttpClient` of more than one relay keeps to one chain** (feature `http`). It asks each relay for its node configuration before the relay's first use and never asks a relay of another chain anything else, so a failover cannot reach one. The chain is the one given, with `HttpClient::for_chain(relays, identity)` or `HttpOptions::identity` (`Chain::relay_identity` of a loaded chain, or `Profile::relay_identity` of a profile that pins the network hash), or else the one of the first relay the client checks, which it learns then; `HttpClient::identity` says which. A client of one relay without an identity checks nothing. Such a client now sends one more request per relay, a node configuration, before the relay's first use, and a relay whose configuration cannot be read is skipped. A struct literal of `HttpOptions` needs the new field `identity`, or `..HttpOptions::default()`. The crate's README and the `iceroot-sdk` documentation show a `connect` that gives the client the pinned chain.
- **`HttpClient` follows no redirect** (feature `http`): a relay that answers with one is skipped like a relay that cannot be reached, so a request, its headers and its body never reach a host the relay list does not name. A proxy named by `HTTP_PROXY`, `HTTPS_PROXY` or `ALL_PROXY` in the environment is used, as curl uses it. On Android the client verifies HTTPS against the Mozilla root certificates it is built with (`webpki-root-certs`), since the platform's verifier needs the application's Java environment, which a library cannot set up. There a certificate from a private or user-installed authority is refused, the roots are those of the `webpki-root-certs` version in the application's `Cargo.lock` (a root Mozilla adds or distrusts later arrives only with a rebuild: run `cargo update -p webpki-root-certs` before each release of the application), and no certificate revocation is checked.
- **No fee from the node's statistics.** `Draft::build` takes the chain, the request and the online facts; its fee statistics parameter is gone, and so are the `node-statistics` fee source (`FeeSource` is `Floor`, `Explicit` or `Unverified`) and the core's `FeeStatistics` and `FeeFigures`. The client's `fee_statistics` call stays, for display. A serialized draft whose fee source names anything other than `floor` or `unverified` reads as `explicit`.
- **A serialized draft's floor is the floor only on the reader's own chain.** `FeeSource` gains `Unverified` (`"unverified"`). `Draft::deserialize(bytes, profile)` computes the floor under the configuration the serialized form carries, whose fee table the pinned network hash does not cover, so a fee the form calls the floor and that equals that floor now reads `Unverified` instead of `Floor`; the floor is kept for display only. `Draft::deserialize_at(bytes, &chain, height)` reads the draft on a chain the reader loaded itself, at the height of the network's next block, refuses a draft built under another network configuration with `NetworkMismatch` (`MismatchProblem::Configuration`, `details.reason` `configuration`), and reads `Floor` when the fee is that chain's floor at the draft's height, which the builder chose, and the floor at `height` is the same; where a change of the fee table lies between the two heights, it reads `Unverified`. `Draft::deserialize_on(bytes, &chain)` reads a draft the same way without the network's height, and reads `Floor` only when the chain's fee table gives the same floor at every height. A serialized form's `unverified` source claims the floor as `floor` does. The bindings add `draft::deserialize_at` and `draft::deserialize_on`, the Tauri plugin's `draft_deserialize` takes an optional `session` (a connected network of the page) to read on its chain at its next height, and the Go SDK's module reads `draftRead` and `draftSign` on the chain of an optional `configuration`, at an optional `height`. Code that matches every `FeeSource` needs the new variant.
- **No floor without an enabled fee table.** Where the milestone in force has no enabled dynamic fee table, the node's pool applies settings of its own, so there is no floor: `Chain::fee_floor` and `ResolvedFee::floor` are `None`, `Rules::fees.floor_available` is `false`, and `FeeChoice::Minimum` and multipliers fail with `FeeUnavailable`. Such a network needs `FeeChoice::Exact`. A draft never carries a zero fee labelled as the floor.
- **Messages are never a proof, and a sign-in is signed after its checks.** `message::sign` and `message::sign_bytes` refuse with `InvalidArgument` text whose first line is an ownership proof's: a devnet account imported from a Solar passphrase holds the Solar key, and a proof is made only by `ownership::sign` or from a signature made elsewhere. `signin::sign(profile, account, message, origin, now_ms)` signs a website's sign-in message only once it passes `signin::parse` against the origin of the page that asks and the account's own public key and address; a wallet uses it rather than `message::sign` from a generic prompt, since a page of another origin can relay a website's challenge. `message::sign`, `sign_with`, `sign_bytes` and `sign_bytes_with` now also refuse, with `InvalidArgument` and the reason "a sign-in message is signed only for the page that asks for it, never as a plain message", any text that `signin::parse` accepts for some network, origin, account and time, a lapsed challenge included; so do the bindings' `Key::sign_message`, the Go SDK module's operation `signMessage` and the Tauri plugin's command `key_sign_message`. A wallet that signed a website's sign-in message as a plain message signs it with `signin::sign` (or `Key::sign_sign_in`, `signinSign`, `key_sign_sign_in`) instead. Signatures and their verification are unchanged. The bindings add `Key::sign_sign_in`, the Go SDK's module the operation `signinSign`, and the Tauri plugin the command `key_sign_sign_in`, which `iceroot:default` allows.
- **`keystore_decrypt` is out of the Tauri plugin's default permissions.** An application opens accounts with `key_from_keystore`, which keeps the phrase in Rust; one with a screen that shows the phrase again grants `iceroot:allow-keystore-decrypt` in its capability.
- **A vote reason's declared value cannot set text apart with blank space.** In the sentences of `Reason` and `Shortfall`, a value a validator declared (an operator or hosting name) is quoted and escaped as before, and every space of a run of two or more ASCII spaces is now written as `\u{20}`, so a padded name cannot push the text after it onto what looks like a line of its own in a renderer that wraps.
- **A node's text is escaped as every SDK escapes it.** Where the node API client keeps text a node chose (the message and name of a refusal, a rejected transaction's code and message, a value a decoder refuses), it now writes every control and format character, line and paragraph separator and space other than the ASCII space (the Unicode categories Cc, Cf, Zl, Zp and Zs) as an escape such as `\u{ad}`, as the TypeScript and Go SDKs do; before, a soft hyphen, the invisible format characters outside a fixed list and the wide spaces stayed as they were.
- **A node's status corrects a Tauri connection's height.** The plugin kept the highest height any successful answer's `X-Block-Height` reported, so one answer of a relay could hold the connection's height, and the rules and economics of its next block, far ahead for the rest of the session. A status read now sets the height, even lower, and a header's height counts only when it is above the last status's, as in the TypeScript package's WebAssembly entry. A read's `height` can therefore go down after `node.status()`.
- **heartwood-core's address.** `heartwood-crypto` is fetched from `https://github.com/iceroot-network/heartwood-core.git`. No key or token is needed.

It also carries the vote selection library, the keystore and ownership proofs:

- **`iceroot-vote`**, re-exported as `iceroot_sdk::vote`, with `iceroot_sdk::voting` to build a snapshot from the node client's validator list. It selects a vote in four modes (Diversity, Reliability, Maximum Rewards, Support Newcomers), sampled per account and reproducible, and splits and checks votes against the network's rules. Validators a node refuses votes for are left out of a relay snapshot.
- **`iceroot-keystore`**, re-exported as `iceroot_sdk::keystore` behind the default feature `keystore`: a versioned encrypted format for recovery-phrase entropy (Argon2id and XChaCha20-Poly1305, every header byte authenticated), with presets for desktop, mobile and web. Backends that never hold a user's seed can leave it out with `default-features = false`.
- **`iceroot_sdk::ownership`**: build, sign and verify version 1 ownership proofs of Solar addresses, as the legacy signer makes them, for claims.
- **`Mnemonic::entropy()`**, the phrase's entropy, for the keystore.
- **`tauri-plugin-iceroot`**: the SDK as a Tauri 2 plugin, the native implementation of the TypeScript package's interface (`@iceroot-network/sdk/tauri`) for desktop and mobile wallets. Keys and signing stay in Rust behind handles that belong to the webview that opened them, drafts cross as serialized bytes and are read again before signing, node requests go over reqwest to the relays the application's capabilities allow, and the keystore runs natively. It is a workspace of its own (it builds against Tauri and the platform's webview libraries); checked on Linux, built for Android.
- **`HttpClient::exchange`** (feature `http`): sends a request and decodes its answer with the caller's decoder, with the same failover, request budget and backoff as `send`, for a host that keeps its calls in another form.
